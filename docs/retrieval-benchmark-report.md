## 二、测试结果汇总

### 2.1 本地 `/search` 覆盖测试：19/19 PASS

用例覆盖：三项目通用场景（注册登录/密码加密/分页/删除）、各项目业务特性、符号检索、英文检索、跨库混合、业务分支感知、无意义查询边界。

全部命中预期文件，且跨库查询能同时召回三个项目、按相关度正确排序。业务分支（feature/task-stats）diff 索引正常，仅该分支存在的新文件（statsService/stats.js/回收站逻辑）可被检索。

### 2.2 云服务器 `/search`：2/15 PASS（重灾区）

| 问题 | 现象 | 根因 |
|---|---|---|
| **全局搜索 0 结果** | 所有不传 repo_id 的查询（跨库/通用）返回空 | 云镜像为旧版本：全局搜索硬编码 `branch="main"` 过滤，而 springboot 默认分支是 `master`，数据全在 master 下。**该 bug 本地已修复**（`_resolve_branch` 对全局搜索返回 `None` 不做分支过滤），云上未部署 |
| **查询超时** | 「注册登录」「密码加密」等 60s 超时 | 全局搜索在错误分支下空转 + 云服务器 CPU 推理慢 + BM25 全表扫描 |
| **测试文件误排** | 「用户列表查询」top1 为 `UserMapperTest.java` | 测试文件权重（0.5）不足以压过 M3 对测试类的高打分 |
| **LoginVO 误排** | 「登录校验和 token 生成」top1-3 全是 `LoginVO.java`（getter/setter） | M3 交叉编码对含 token 字段的短片段打分恒高（见 3.2） |

业务分支（feature/codepop-test）在云上可正常识别（`actual_branch` 正确、无 fallback）。

## 三、三项目差异与共同点分析

### 3.1 共同点（检索系统应稳定处理的共性）

1. **用户认证是三大项目共同核心**：注册/登录/令牌/密码——检索系统对「登录流程」这类通用语义必须跨项目稳定命中。
2. **标准 CRUD + 分页列表**：三个项目都有列表分页查询，检索需区分「实现分页的 service」与「前端调用处」。
3. **中文 query 为主**：三个项目测试均以中文语义查询驱动，对中文→代码的映射能力是通用关键路径。

### 3.2 差异点（暴露系统弱点的放大镜）

| 差异 | 检索表现 |
|---|---|
| **静态资源比例**（PyFly 18/49 是 layui JS） | 压缩 JS 在符号/图路径高频命中，需 `static` 角色降权（本地已做 0.3，仍会在部分用例进入 top3，可继续调低） |
| **代码注释密度**（MT 最密、spring 最疏） | 注释越少，中文语义命中越依赖 SEMANTIC_MAP 扩展词与英文对齐；spring 的「登录」用例被 VO 类反超即是注释少 + 字段名恰好含关键字的典型场景 |
| **数据类 vs 实现类**（LoginVO vs LoginServiceImpl） | M3 交叉编码偏好短而关键词密集的片段（getter/setter），对「实现逻辑」类长片段打分偏低——**这是跨项目共性缺陷**，非 springboot 特有 |
| **默认分支命名**（master vs main） | 全局搜索若硬编码任一分支名必然漏掉另一命名，必须按仓库 default_branch 动态处理 |
| **业务分支代码形态** | 分支 diff 为「纯新增前端」（spring）或「新模块」（MT），检索需按 (query, branch) 正确限定 |

## 四、问题与根因分析

### 4.1 全局搜索 0 结果（云，P0）
**根因**：`SearchQuery.branch` 默认 `"main"`，全局搜索（repo_id=None）直接拿 `"main"` 过滤 `e.branch`，而仓库 default 是 `master`。定向搜索经 `_resolve_branch` 回落到 default_branch 所以正常；全局搜索无回落逻辑。
**状态**：本地已修复（`_resolve_branch` 对全局搜索返回 `None` = 不过滤分支，所有检索路径兼容），云上需重新部署镜像生效。

### 4.2 M3 交叉编码中文打分失真（P1，跨项目）
**根因**：bge-reranker-base 主要训练于英文文本，「中文问句 vs 英文代码片段」的交叉编码分数整体坍缩且相对排序不可靠，偏好短而关键词密集的片段（VO/DTO/getter），压过真正的实现代码。
**证据**：
- 「登录校验和 token 生成」→ LoginVO getter/setter 0.445 vs LoginServiceImpl 实现 0.016
- 「发帖后可以收藏帖子吗」→ M3 给全部候选 <0.001，纯按模型偏好重排
**状态**：本地已做「中文 query 用 原文+英文扩展词 混合喂 M3」（相对提升明显，4 用例转正），但 LoginVO 类数据片段仍可排前——需调参兜底。

### 4.3 无意义查询有结果（P2）
「香蕉星系量子跃迁引擎」仍返回 5 条结果。向量检索必然返回 top-k，无相关度下限。需要相对分数阈值过滤。

### 4.4 测试文件/前端文件误排（P3）
「用户列表查询」云上 top1 是 `UserMapperTest.java`，本地 top1 是前端 `user.js`。`test` 权重 0.5、`web` 权重 0.8 在 M3 高分面前压不住。

### 4.5 性能分化（P4）
PyFly 与全局查询 7-19s，spring/MT 1.5-2s。根因：BM25 SQL 全表扫描（debug 显示 bm25 路径 4-13s）+ 概念扩展膨胀 + 无 GPU 的 CPU 推理。静态 JS 占比高的仓库 tsvector 匹配面更大。

## 五、改造建议（约束：不引新包、不重打包镜像、影响面小、不过拟合单项目）

> 已完成的代码级修复（全局分支、M3 中文混合、static 降权）属于**通用 bug 修复**，本地已验证，云上需部署含修复的镜像才能生效——这不属于「新增改造」，是让线上与本地对齐的必要一步。
> 以下新增优化全部为**调参/流程级**，改动集中在常量与阈值，无需新依赖。

### 5.1 调参项（低风险，改数值即生效）

| 参数 | 现状 | 建议 | 针对问题 | 通用性 |
|---|---|---|---|---|
| `ROLE_WEIGHTS["static"]` | 0.3 | 0.2 | P4 静态 JS 干扰 | 前端构建目录通用约定 |
| `ROLE_WEIGHTS["test"]` | 0.5 | 0.3（与 how_it_works 对齐） | P3 测试文件误排 | 任意项目测试目录 |
| M3 后重排对 `dto/model` 权重 | 0.75/0.8 | 0.6/0.7，并让 `vo` 目录落回 `model` 角色 | P1 LoginVO 误排 | 数据类通用特征 |
| M3 中文混合英文扩展词数 | 6 个 | 保持或 4-8 区间按效果微调 | P1 | 已生效 |

### 5.2 流程优化项（低风险）

1. **无意义查询过滤**：对 M3 重排后的 top1 分数做相对阈值判断（如 top1 与 top2 差距或绝对分数低于经验值则返回空）。需先在真实数据上统计分数分布确定阈值，**验证后才落地**，避免误杀有效查询。
2. **BM25 性能**：概念扩展词数量已有上限（10），可进一步：去除停用词/单字概念；`bm25` 路径 `top_k` 由 20 降至 12（召回到重排阶段足够）；`sparse` 路径 `top_k` 同步下调。降低 PyFly/全局场景延迟。
3. **hnsw `ef_search`**：128 → 64（召回略降、延迟显著降），仅在性能瓶颈明显时启用，配合 benchmark 对比。

### 5.3 不建议做的（避免过拟合）

- 为 springboot 单独加「VO 文件名黑名单」——属于单项目特判，拒绝。
- 为 PyFly 排除 `static/` 目录——已有通用 `static` 角色，无需特判路径。
- 引入新重排模型/新分词库——违反「不引新包」约束，且 M3 调参已足够。

### 5.4 落地优先级

1. **云上部署含本地修复的镜像**（P0 全局搜索修复 + M3 混合 + static 降权），一次对齐本地
2. 调参项（5.1）随下次发布一并生效，无需单独打包
3. 流程优化（5.2）在 benchmark 回归确认后启用

---

## 六、结论

1. 本地（含近期修复）检索质量达标：19/19 命中，业务分支 diff 索引正确，跨库/跨分支排序合理。
2. 云上核心问题是**未部署本地修复**导致的全局搜索瘫痪（P0），非检索算法问题；LoginVO 误排与性能分化是本地、云共有的通用调参空间。
3. 三项目对比验证了检索系统的通用路径（认证/CRUD/分页）稳定，差异点（静态资源、注释密度、数据类）指向的优化全部有通用落点，可用调参+流程优化收敛，无需新包、无需重打包。
